# Design: multi-variable codebooks with neutral field names (R1.1)

Status: draft, revision 1 — first pass, not yet red-teamed. Per
`docs/ROADMAP.md`'s own instruction for this brief ("get the author's
sign-off on the YAML shape before writing code"), **no implementation
should start from this document until the author has reviewed it.**

## Context

`docs/ROADMAP.md` R1.1, sourced from
[`docs/research/2026-09-02_state_of_the_project_diagnosis_and_distribution.md`](../../research/2026-09-02_state_of_the_project_diagnosis_and_distribution.md)
finding #1 (the highest-ranked drift item): today a codebook is exactly one
concept with one set of categories, and the LLM output schema is fixed to
three Portuguese-named fields — `categoria`, `justificativa`,
`trecho_evidencia`. These are hardcoded, by exact name, in:

- `src/text_as_data/codebook.py` (`Codebook._from_spec`'s `create_model`
  call, `build_messages`)
- `src/text_as_data/db.py` (`ExtractionRecord`)
- `src/text_as_data/extraction.py` (`run_extraction`'s unwrapping of the
  provider result)
- `src/text_as_data/app.py` (`get_run_results`, `update_extraction`,
  `upload_gold_labels`'s `gold_categoria` CSV column, `get_run_validation`)
- `frontend/src/api.ts` (`ExtractionResult`, `updateExtraction`) and
  `frontend/src/ResultsTable.tsx` (rendering, filtering, inline edit)

`src/text_as_data/export.py` and `src/text_as_data/validation.py` are
**already** field-name-agnostic (`export.py` operates on `list[dict]`;
`validation.py`'s `agreement_report()` already accepts a `columns: list[str]`
parameter for comparing more than one field at once, even though nothing
has exercised it with more than one column yet). Verified by reading both
files in full — this matters because it means a real chunk of R1.1's
apparent scope is "start using a capability that already exists," not new
code, which lowers this spec's risk relative to how large the brief reads.

A general-purpose codebook tool must ask several questions per document
(Halterman & Keith's own codebooks do — `AGENTS.md`'s own codebook-format
section already models the *desired* field names as `category`,
`rationale`, and `evidence_span`, not the Portuguese names actually
implemented; this spec adopts those three names).

**Live conflict this spec must not make worse**: session `cifra-text-as-data-29`
is mid-way through several-hour, real-LLM-call experiments (joint
hypothesis-pair scoring, persona ablation, reproducibility repeat-run)
against `pilot_v7.py` and the current `Codebook.build_messages(text)`
single-argument signature. They asked (2026-09-02) to hold off moving
`pilot_v7.py` or changing `Codebook`/`run_extraction` signatures until
those experiments are committed. This spec is written to make that
transition as painless as possible (see "Backward-compatible call
signature," below) but **implementation must still wait for their
explicit all-clear**, not just for author sign-off on this document.

## Design questions from the brief, answered

### 1. YAML shape

Add an optional `variables:` list. Each entry has `name`, `description`,
and `categories` (identical shape to today's category list — `label`,
`definition`, `positive_examples`, `negative_examples`, `boundary_notes`).
Today's single-variable shape (`categories:` directly under the top level)
stays valid as shorthand and is normalized internally to a single variable
named `"category"` — chosen because that's the fixed English field name
this project already uses for the concept everywhere else (`AGENTS.md`,
this spec's own field-name decision below), not `concept` (which stays
the whole-codebook *title*, not a variable identifier) and not `label`
(already means something else one level down).

```yaml
# Today's shape, still valid, unchanged:
concept: protest
description: A collective public event expressing a political or social claim.
categories:
  - label: protest
    definition: ...
  - label: not_protest
    definition: ...

# New multi-variable shape:
concept: protest_coverage
description: >
  Whether a news article describes a protest, and if so, how the article
  frames the police response.
variables:
  - name: is_protest
    description: Whether this document describes a protest event.
    categories:
      - label: protest
        definition: ...
      - label: not_protest
        definition: ...
  - name: police_framing
    description: How the article frames the police response, if any.
    categories:
      - label: supportive
        definition: ...
      - label: critical
        definition: ...
      - label: neutral_or_absent
        definition: ...
```

`validate_spec` rejects a spec that supplies **both** top-level
`categories` and `variables` (ambiguous — which one is authoritative).
Within `variables:`, each `name` must be a non-empty string, unique across
the list (same style of check `validate_spec` already does for category
`label`s), and each variable's own `categories` list is validated with
the exact same per-category logic already in `validate_spec` today
(refactored into a helper so it isn't duplicated). Category labels only
need to be unique *within* their own variable, not across variables (two
different variables are allowed to both have a `low`/`high` category, for
instance).

### 2. Output field names

`category`, `rationale`, `evidence_span` — replacing `categoria`,
`justificativa`, `trecho_evidencia` everywhere. These are the exact names
`AGENTS.md`'s codebook-format section already uses to describe the
intended output ("a free-text `rationale` field and an `evidence_span`
field"), so this spec is bringing the implementation in line with the
project's own documented design, not inventing new names.

### 3. Row shape: one row per (document, variable)

`extractions` stays a narrow table: one `ExtractionRecord` row per
(document, variable), not one row per document with a JSON blob. Reasons:

- Every existing per-row operation (`PUT .../results/{id}` inline edit,
  the cache lookup, the error-row-on-failure path, the audit-trail
  `prompt_sent`/`raw_response` pair) already assumes "one row = one
  category decision with its own exact prompt and response." A JSON
  column would force every one of those to parse/rewrite a blob instead
  of touching one field, and would make `prompt_sent`/`raw_response` per
  *variable* impossible to represent cleanly (today's audit trail is
  explicitly "the exact prompt sent" for one decision — a multi-variable
  JSON blob would blur that back into "the exact prompt sent for
  everything," which is a real loss of the auditability this project
  treats as its differentiator).
- Filtering ("show me all `police_framing=critical` rows") and the
  validation report ("per-variable accuracy") are both plain `WHERE`
  clauses on a narrow table; both would need JSON-path queries or an
  application-side unpack on a wide table.
- `HumanLabelRecord` (gold labels) already works this way (one row per
  document, soon to need `variable` too — see §6) — keeping predicted and
  gold rows structurally parallel keeps `agreement_report()`'s merge
  logic simple.

Cost: a run against an N-variable codebook writes N× the row count it
does today for the same corpus. This is judged acceptable — it's the same
row-count growth the LLM-call-count growth already implies, and
`get_run_results` already returns a flat list the frontend groups
client-side, so pagination (not in scope for R1.1; `R5.2` in the roadmap)
is the real long-term answer to row count, not a schema choice here.

### 4. Prompt strategy: one call per variable (not one call per document for all variables)

Chosen over a single joint call that returns every variable at once, for
three reasons:

1. **Audit trail stays exact.** One call → one variable's `prompt_sent`/
   `raw_response`, unambiguous. A joint call's raw response would have to
   be split after the fact to populate N rows' `raw_response`, which is
   either a lossy summary or N copies of the same blob pretending to be
   per-variable.
2. **Cache invalidation stays precise.** Editing one variable's
   `categories` (say, adding a `police_framing` category) must not force
   every other variable's already-good, already-cached extractions to be
   thrown away and re-billed. A joint call's natural cache key is the
   *whole* codebook's content hash — editing anything invalidates
   everything. A per-variable call's cache key is that *variable's own*
   content hash (see §7) — editing `police_framing` leaves `is_protest`'s
   cache untouched.
3. **Retry stays cheap and precise.** `_extract_with_retry` retries one
   provider call. If document X fails only on `police_framing` (a
   malformed-JSON hiccup in CLI mode, say), a per-variable design retries
   only that one call; a joint call would have to retry (and re-bill) the
   whole document's every variable to fix one.

Real cost: N variables means N LLM calls per document, and the full
document text is resent in each call's prompt (no cross-variable
consistency the way one joint call could offer, and no token savings from
sharing a single call's context across variables). This is a deliberate
trade of raw cost for the caching/audit/retry precision this project has
consistently chosen elsewhere (see `extraction.py`'s existing content-hash
cache, added specifically so an edited codebook can't silently reuse
stale extractions). A joint one-call-per-document mode is left as a
documented future option (see Non-goals) if real usage shows the API cost
matters more than these guarantees for a given codebook.

### 5. Gold-label CSV: one `gold_<variable>` column per variable

`gold_is_protest`, `gold_police_framing`, etc. — one column per declared
variable name, each independently optional per row (blank = "not yet
reviewed for this variable," same semantics as today's single
`gold_categoria`). `upload_gold_labels` iterates the codebook's variable
names to know which columns to look for, and writes one `HumanLabelRecord`
per (document, variable, non-blank value) — same all-or-nothing validity
rule as today (any non-blank value that isn't a real category for that
specific variable rejects the whole upload, with every bad row/column
combination listed).

### 6. Validation report keyed by variable

`GET /runs/{run_id}/validation` returns `{"per_variable": {"is_protest":
{...}, "police_framing": {...}}}` where each value is the same shape
`get_run_validation` returns today (`coverage`, `per_category`,
`disagreements`). Implementation: pivot the narrow `extractions`/
`human_labels` tables into one wide `predicted` DataFrame and one wide
`gold` DataFrame (one column per variable, one row per document — a
`pandas.pivot`), then call **the existing, unmodified**
`agreement_report(predicted, gold, id_col="document_id",
columns=[v.name for v in variables])` — already designed for exactly this
(§ Context). `validation.py` needs zero code changes; only its caller in
`app.py` changes.

### 7. `pilot_v7.py` relocation

Move to `scripts/pilot_v7/` (keeping it next to
`scripts/run_v7_candidates_via_agy.py` and `scripts/import_v7_pilot.py`,
which already import from it) rather than `examples/` — it's a working
research script tied to one specific dataset and study, not a
demonstration of the library's general API the way `examples/` implies.
`src/text_as_data/` keeps nothing V7-specific.

**Deferred, not scheduled by this spec**: this move touches files
`cifra-text-as-data-29` is actively reading/writing during their
in-progress experiments. Do not execute this move until they confirm
completion (see Context). This spec only records the target location so
the eventual move is a mechanical `git mv` + import-path fix, not a
design decision made under time pressure later.

## Data model changes (`src/text_as_data/db.py`)

```python
class ExtractionRecord(SQLModel, table=True):
    __tablename__ = "extractions"

    id: int | None = Field(default=None, primary_key=True)
    run_id: int = Field(foreign_key="runs.id")
    document_id: int = Field(foreign_key="documents.id")
    variable: str = "category"          # NEW — the codebook variable this
                                         # row answers. "category" is the
                                         # normalized name for a legacy
                                         # single-variable codebook (§1),
                                         # so old rows read back correctly
                                         # under `_ensure_columns`'s
                                         # existing ADD-COLUMN-with-DEFAULT
                                         # migration with zero extra code.
    category: str                       # RENAMED from categoria
    rationale: str                      # RENAMED from justificativa
    evidence_span: str                  # RENAMED from trecho_evidencia
    tokens_used: int | None = None
    prompt_sent: str = ""
    raw_response: str = ""


class HumanLabelRecord(SQLModel, table=True):
    __tablename__ = "human_labels"

    id: int | None = Field(default=None, primary_key=True)
    document_id: int = Field(foreign_key="documents.id")
    codebook_id: int = Field(foreign_key="codebooks.id")
    variable: str = "category"          # NEW — same normalization as above
    category: str                       # unchanged name, already neutral
    coder: str
    source: str = "manual"
    layer: str = "final"
    created_at: datetime = Field(default_factory=lambda: datetime.now(timezone.utc))
```

`variable` on both tables is additive — `_ensure_columns` already handles
"add a column with a scalar default to an existing table" automatically
(it's exactly what added `prompt_sent`/`raw_response` and
`provider_mode`/`provider_detail` before, per `db.py`'s own docstring), so
no manual migration step is needed for that part.

**The three renames (`categoria`→`category`, `justificativa`→`rationale`,
`trecho_evidencia`→`evidence_span`) are not additive** — `_ensure_columns`
explicitly never renames a column (by design, to never risk data loss on
an ambiguous rename). Per the brief's own allowance ("backwards
compatibility of the *database* matters less... but write a one-shot
migration for the author's own `codifica.sqlite` anyway"), this spec adds
a one-shot script:

```python
# scripts/migrate_r1_1_field_names.py
# Run once, by hand, against the author's own codifica.sqlite before
# first use of R1.1 code against it. Prints what it did; refuses to run
# twice (checks whether `category` already exists before renaming).
ALTER TABLE extractions RENAME COLUMN categoria TO category;
ALTER TABLE extractions RENAME COLUMN justificativa TO rationale;
ALTER TABLE extractions RENAME COLUMN trecho_evidencia TO evidence_span;
```

(SQLite's `ALTER TABLE ... RENAME COLUMN` has been supported since SQLite
3.25.0 (2018); the Python versions this project targets all bundle a
newer `sqlite3` than that, so no compatibility shim is needed.) A fresh
`codifica.sqlite` (any new user, any test) never needs this script —
`create_all()` creates the renamed columns directly.

## `src/text_as_data/codebook.py` changes

```python
@dataclass
class CodebookVariable:
    name: str
    schema: type[BaseModel]      # {category: Literal[...], rationale: str, evidence_span: str}
    instructions: str
    examples: list[dict] = field(default_factory=list)

    def build_messages(self, text: str) -> list[dict]:
        ...  # exactly today's Codebook.build_messages body, unchanged


@dataclass
class Codebook:
    concept: str
    description: str
    variables: dict[str, CodebookVariable]   # insertion-ordered; >=1 entry

    def build_messages(self, text: str, variable: str | None = None) -> list[dict]:
        """Backward-compatible with the pre-R1.1 single-argument call.
        `variable=None` requires exactly one entry in `self.variables` and
        uses it — this is what keeps any code still calling
        `codebook.build_messages(text)` (pilot_v7.py's helper scripts,
        today, until they migrate) working unchanged for single-variable
        codebooks specifically, which is the only case they use."""
        if variable is None:
            if len(self.variables) != 1:
                raise ValueError(
                    "build_messages() needs an explicit variable= for a "
                    "multi-variable codebook"
                )
            variable = next(iter(self.variables))
        return self.variables[variable].build_messages(text)

    @classmethod
    def _from_spec(cls, spec: dict) -> "Codebook":
        validate_spec(spec)
        variable_specs = _normalize_variables(spec)   # §1's shorthand expansion
        variables = {
            vs["name"]: _codebook_variable_from_spec(vs) for vs in variable_specs
        }
        return cls(concept=spec["concept"], description=spec["description"], variables=variables)
```

`_codebook_variable_from_spec` is today's `_from_spec` body (schema
`create_model` + instructions-string building), factored out unchanged
except for the three field renames and operating on one variable's
`categories` instead of the whole spec's.

`Codebook.schema`/`Codebook.instructions` (today's flat attributes) are
**removed**, not deprecated-and-kept — every real call site in this
repo (`extract()`, `run_extraction`, `pilot_v7.py`) is being updated by
this same piece of work, so there's no external consumer to keep a shim
for, and a silent shim would hide exactly the kind of "which variable did
this actually run against" ambiguity this whole spec exists to remove.

## `src/text_as_data/extraction.py` changes

`extract()` (the low-level `pandas`-in/out helper) gains a `variable: str
| None = None` parameter, threaded straight through to
`codebook.build_messages(row[text_col], variable)` — same
backward-compatible default as above.

`run_extraction()`'s per-document loop becomes a per-(document, variable)
loop:

```python
for document in documents:
    for variable_name, variable in codebook.variables.items():
        variable_hash = hashlib.sha256(
            json.dumps(_variable_spec_slice(codebook_record's yaml, variable_name), sort_keys=True).encode()
        ).hexdigest()
        # cache lookup now also filters on ExtractionRecord.variable == variable_name
        # and matches the stored per-variable hash, not RunRecord.codebook_yaml_hash
        ...
```

**Cache key changes from `(document, codebook_yaml_hash, model)` to
`(document, variable, variable_spec_hash, model)`**, where
`variable_spec_hash` hashes only that variable's own normalized
sub-spec (name + description + categories), not the whole YAML file. This
is what makes §4's per-variable cache-precision claim actually true — a
new column `ExtractionRecord.variable_spec_hash: str = ""` is needed
alongside `variable` to store it (additive; same `_ensure_columns`
mechanism). `RunRecord.codebook_yaml_hash` stays as-is (still useful for
disclosure/provenance — "what was the whole codebook at run time" — even
though it's no longer the cache-matching key).

A single document's single-variable failure still only produces one
`__error__` row for that (document, variable) pair, exactly like today's
per-document error isolation — a `police_framing` failure does not block
`is_protest` from succeeding for the same document.

## `src/text_as_data/app.py` changes

- `GET /runs/{run_id}/results` — rows now include `variable`. Add an
  optional `?variable=` query filter. No other shape change; the frontend
  groups by document client-side (see Frontend, below).
- `PUT /runs/{run_id}/results/{extraction_id}` — request body renamed
  `{category, rationale}`; validates `category` against *that row's own
  `variable`*'s category labels (look up the matching `CodebookVariable`
  by `extraction.variable`, not the whole codebook's — today's single-
  variable code implicitly only had one label set to check against).
- `POST /runs/{run_id}/gold-labels` — reads one `gold_<variable>` column
  per declared variable (§5); unmapped/blank stays "not yet reviewed" per
  column independently (a row can have `gold_is_protest` filled and
  `gold_police_framing` blank).
- `GET /runs/{run_id}/validation` — returns `{"per_variable": {...}}`
  (§6), computed via a pivot + the existing `agreement_report()`.
- `GET /runs/{run_id}/export` — CSV/XLSX export pivots to one row per
  document with per-variable column groups
  (`category_is_protest, rationale_is_protest, evidence_span_is_protest,
  category_police_framing, ...`) — this is the shape a researcher actually
  wants to open in a spreadsheet (one row = one document, scan across for
  every variable), not one row per (document, variable) forcing a manual
  pivot on their end. JSON export instead nests: one object per document
  with a `variables: {is_protest: {...}, police_framing: {...}}` map —
  JSON has no "spreadsheet flattening" expectation, and nesting is more
  faithful to the actual data shape than flattening would be.
- `POST /corpora/{corpus_id}/import-qualilab-labels` and
  `POST /runs/{run_id}/export-qualilab` — both gain a required `variable:
  str = Form(...)` alongside the existing `category_id`, since a QualiLab
  attribute maps to exactly one Cifra variable, and there is no longer a
  single implicit variable to assume.

## Frontend changes (design-level; exact layout is implementer's call)

- `frontend/src/api.ts` — `ExtractionResult` gains `variable: string`;
  `category`/`rationale`/`evidence_span` replace the Portuguese names;
  `updateExtraction` signature follows.
- `frontend/src/CodebookEditor.tsx` — needs a repeatable "variable" block
  (name + description + the existing category-list sub-editor, reused
  once per variable) instead of one fixed category list. This is the
  largest frontend change in this brief and deserves its own short design
  note before implementation (not fully specified here) — at minimum: can
  a user add/remove/reorder variables, and does the live YAML preview
  render the shorthand form when there's exactly one variable (matching
  what a hand-written single-variable YAML file looks like) or always the
  explicit `variables:` form?
- `frontend/src/ResultsTable.tsx` — results are grouped by `document_id`
  client-side into one row per document with one column group per
  variable (mirroring the CSV export shape above), plus a variable
  selector alongside today's existing category filter.
- `frontend/src/ValidationPanel.tsx` — one section per variable (e.g.
  tabs, or stacked panels), each rendering today's existing
  coverage/per-category/disagreements layout unchanged.

## Testing

- `codebook.py`: shorthand YAML still normalizes to
  `variables == {"category": ...}`; explicit `variables:` YAML with 2+
  entries validates and derives 2+ independent schemas; duplicate
  variable `name` rejected; both `categories` and `variables` present at
  once rejected; duplicate category labels *within* one variable rejected,
  but the same label allowed to repeat *across* variables.
- `build_messages(text)` with no `variable=` works for a single-variable
  codebook and raises `ValueError` for a multi-variable one (the
  backward-compatibility contract in §"Codebook.build_messages", tested
  explicitly since `pilot_v7.py`'s scripts depend on it not breaking).
- `extraction.py`: a 2-variable codebook run produces 2 `ExtractionRecord`
  rows per document; editing only variable B's categories (same codebook
  id, new yaml) invalidates variable B's cache but not variable A's
  (the precision claim in §4, tested directly — this is the test most
  likely to catch a mistake in the hashing change); one variable's
  provider failure produces an error row for only that variable, and the
  other variable's row for the same document still succeeds.
- `app.py`: results/validation/export/gold-labels round-trip for a
  2-variable codebook end to end; `PUT .../results/{id}` rejects a
  `category` value valid for the *other* variable but not this row's own;
  gold-label upload with one variable's column present and the other
  absent still imports the present one; export pivots correctly with a
  document missing a row for one variable (partial run/error case).
- Migration script: a copy of a real pre-R1.1 `codifica.sqlite` fixture
  (or one built in the test with the old schema) round-trips through
  `scripts/migrate_r1_1_field_names.py` and reads back correctly under the
  new model; running the script twice is a no-op with a clear message,
  not an error on the second run.
- Full existing single-variable test suite still passes, with field names
  updated (`categoria`→`category` etc.) throughout — this is the
  brief's own stated acceptance bar for "nothing regressed."

## Explicit non-goals (this revision)

- A joint one-call-per-document mode that returns all variables in one
  LLM response (§4) — left as a documented future option if real usage
  shows per-variable call volume is a real cost problem; not built now.
- Cross-variable consistency checks (e.g. "if `is_protest=false`, require
  `police_framing=neutral_or_absent`") — a codebook-authoring concern, not
  a pipeline one; nothing here prevents a researcher from encoding that as
  a boundary note today.
- Actually moving `pilot_v7.py` (§7) — location is decided, execution is
  deferred pending `cifra-text-as-data-29`'s in-progress experiments.
- Any UI-level design for `CodebookEditor.tsx`'s multi-variable authoring
  flow beyond the shape sketched above — flagged as needing its own short
  pass before that specific file is touched.
- Pagination of results/exports for very large corpora (`R5.2`) — the row
  count growth this spec introduces makes that timeline shorter, but
  doesn't change what needs to be built.
